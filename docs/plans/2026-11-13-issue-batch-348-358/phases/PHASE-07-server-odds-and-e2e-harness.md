## Contradictions to read before starting

- R14 reverses two assertions in `volumes.rs`. The test `the_running_app_image_mount_is_hidden_before_it_is_read` asserts that `/tmp/.mount_OtherY` with `fuse.Other.AppImage` stays shown (`hidden.len() == 1`, `kept.len() == 3`) and that a `.mount_` mount is not hidden when no executable is known ("without the executable nothing matches"). R14 says the opposite for a read-only FUSE mount whose last component starts with `.mount_`. Task 7.1 rewrites those assertions on purpose; the fs-name-only marker (`fuse.<image file name>` outside a `.mount_` directory) keeps requiring the executable.
- R45 names the "pairing rejection" log at `debug` in `auth/http.rs`. The only such log is `invalid_pairing_offer_response`, which logs `invalid pairing offer: {detail}` at `debug` while the client receives only `reason: "invalid_pairing_offer"`. That is the offer path. The case the issue saw ("Invalid pairing token" once on LAN pairing) is a rejected pairing credential: `consume_grant` in `auth/service.rs` returns `AuthError::InvalidCredential`, `HttpAuthError::into_response` logs nothing for it, and the client sees `reason: "invalid_credential"` for every cause. Task 7.4 covers both paths.

The credential column holds the credential text, so the lookup uses the presented text and the text is never logged. A credential too malformed to be told from an unknown one (any wrong text) is `unknown`; only the empty string is told apart as `empty`.
