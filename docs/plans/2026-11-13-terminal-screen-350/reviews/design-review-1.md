Verdict: **Needs rework**. The overall approach is sound, but the proposed protocol can lose live output, erase a restored checkpoint during startup handoff, and mix events from different process generations. D5 also omits terminal state needed for continuation; read-only probes against installed xterm 6 reproduced several failures.

What the design got right (so a revision does not break it).

- **The published-byte boundary is correct.** Redaction happens before history insertion and sequence advancement (`manager.rs:3395`). A redactor’s withheld prefix has not yet been published or assigned an output sequence (`:554`); its eventual flush goes through `record_private_output` (`:1963`, `:1973`). Feeding those paths before advancing, and including the emulator’s separate held escape tail exactly once, can make checkpoint S cover every published byte through S. It should **not** flush unpublished redactor input merely to take a checkpoint.
- **The resize hooks are correctly identified:** requested dimensions and retained-size correction both matter (`manager.rs:3952`, `:3993`). Ownership notifications and acknowledgements spend sequences without necessarily changing geometry (`:1823`, `:3938`).
- **Negotiation protects legacy clients.** Optional request/response fields, raw history by default, and per-attachment selection are the right approach. The current Rust attach payload accepts unknown fields (`server_terminal.rs:1677`), and absent capabilities decode false (`packages/contracts/src/environment.ts:74`). Actual mixed-version execution is still required.
- **No inherent publication-lock deadlock is established by D6.** `recv()` invokes `deliver()` after receiving the broadcast (`manager.rs:4823`). A correctly implemented publication→session acquisition can work. However, today’s resync uses operation→session locks (`:4941`, `:4951`), so “under the same locks” is inaccurate and insufficient: the revised algorithm must specify generation capture, rechecking and ordering without holding session while awaiting publication.
- **Raw operational history should remain separate.** Its byte cursors, epochs and dropped-window reporting are independent of visual checkpoint retention (`history.rs:228`, `:302`, `:325`).
- **Profiler direction is appropriate.** D12 uses content-free fields, enabled checks and the existing RPC wrapper, matching `AGENTS.md:145–163`. It needs the lock/lag/resource evidence described above. No new child process or service is proposed for #350.
- Outside the findings above, I found no additional concrete premise defect in **R2–R4, R13–R34 or R36–R47**. This is a source-review conclusion, not evidence that their acceptance tests pass.

Open questions the design cannot answer.

Some of D’s API questions can already be resolved from the cached, pinned **avt 0.20.0** source:

| API question              | Verified answer                                                                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Emulator type             | It exports `avt::Terminal`, **not `avt::Vt`** (`avt-0.20.0/src/lib.rs:89`). The published [0.20.0 documentation](https://docs.rs/crate/avt/0.20.0) agrees.                                        |
| Per-line wrap flag        | Public `Line::is_wrapped()` exists; it means this row continues **onto the next row** (`src/line.rs:568`). Account for that convention when comparing xterm flags.                                |
| Saved cursor and charsets | Private engine state; the saved cursor structure lacks a charset, and the engine has two charset slots (`src/engine.rs:37`, `:102`). D’s G0–G3 claim needs additional implementation or fallback. |
| Scrollback limit          | Public construction-time `with_scrollback` exists (`src/lib.rs:106`); the reviewed public surface has no limit setter. D9’s resize-dependent limit needs a specified implementation.              |
| Dump                      | Public, and includes pending parsing, but explicitly omits retained history and targets a fresh avt terminal (`src/lib.rs:294`). It is not a ready-made xterm checkpoint.                         |
| Pen extension             | Feasible through vendoring, but changing pen fields alone does not implement parsing, link ownership, combined-cell storage and serialization (`src/pen.rs:4`; `src/cell.rs:4`).                  |

Thus vendoring is feasible, but **the claimed three-patch scope and resulting fidelity remain unverified**. The existing Cargo patch/provenance pattern is suitable (`Cargo.toml:156`; `third_party/portable-pty/UPSTREAM.md:1`).

Two other questions are already answerable: browser xterm’s `unicode` getter checks proposed-API permission (`apps/web/node_modules/@xterm/xterm/src/browser/public/Terminal.ts:91`), and restoring focus reporting synchronously reaches `_reportFocus()` (`…/CoreBrowserTerminal.ts:165`, `:1293`). Keep integration tests, but these need not remain unknown design premises.

Still unresolved:

- Can the revised, fully patched serializer pass continuation/reflow tests and memory/latency budgets on Windows and the other supported platforms?
- What request identity fences a cancelled refetch after **clear within the same process generation**, and how does a later renderer restart a cancelled refresh?
- How are real CLI captures isolated and sanitized? Synthetic prompts alone do not exclude private paths, titles or links; committed fixtures must satisfy `AGENTS.md:87–104`.
