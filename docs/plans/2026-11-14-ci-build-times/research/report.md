# Compiling Two Crates Burns Your CI Hours

> **Corrections after review (2026-11-14).** Where this report and
> [measured_ci_and_local.md](measured_ci_and_local.md) differ, the notes are right:
>
> - The split between dependencies and workspace crates in CI comes from when Cargo started each
>   unit, so "80% to 97%" and "the cache saves at most 5 to 7 minutes" are estimates. The two
>   macOS runs compared are different runs and do not measure a cache saving. The one matched
>   comparison (Windows arm64, same commit) shows about 12 minutes saved before the bundle step.
> - "76 minutes compiling one crate" is the sum of five whole Cargo invocations in which
>   `bibcode-server` was the last large unit, not an isolated per-crate time.
> - The one-codegen-unit symbol build was sampled later: `rustc` for `bibcode-server` peaked at
>   9.6 GB, against 8.7 GB with the shipped profile.
> - The `dump_syms` CFI error was reproduced locally and comes from the dSYM, so its cause is
>   known.
> - The macOS doubling is associated in time with the symbol profile; no controlled comparison on
>   that runner exists yet, and memory pressure remains a hypothesis.

CI is slow because two first-party crates, `bibcode-server` and `bibcode-desktop`, plus the final thin-LTO link are compiled from scratch on every run, not because the cache misses. In the measured bundle step they take **80% to 97% of the time**. A full cache match saves only about 5 minutes of a 110-minute macOS build, and an uncached Linux row still finishes in about 29 minutes. The cache problem is real but secondary: the repository holds 9.98 GiB of a 10 GB limit and wants about 17 GB, so 11 of 13 Rust-cache restores in the latest `main` run found nothing. The macOS rows doubled (37-40 to 75-79 minutes) when the symbol profile was switched on, while the same profile changed nothing on a 12-core, 96 GB local Mac. The likeliest explanation is runner hardware: 3 vCPUs and 7 GB of RAM against a compile that peaks at 8.7 GB locally. That explanation is an inference, not a measurement. Windows arm64 adds a separate waste, compiling `bibcode-server` five times in one job (76 of 103 minutes). The ranked fixes are, first, compile each crate once per job; second, stop the cache from thrashing; third, move the symbol build off the 7 GB macOS runner or make it cheaper; fourth, relax codegen-units where the binary's speed allows it.

## What the repository's own measurements show

All figures in this section are measured facts from `measured_ci_and_local.md` (ten `main` runs, 2026-11-04 to 2026-11-14, plus local `--timings` builds). They outrank every external claim below. Local numbers are one run per variant on a loaded machine, so treat them as ballpark.

| Row of run 43562279474 (bundle step)           | Dependencies        | After last dependency to `Finished` | Cargo total  |
| ---------------------------------------------- | ------------------- | ----------------------------------- | ------------ |
| macOS arm64, no cache restored                 | 7 min (527 crates)  | 81 min                              | 87 min 51 s  |
| Linux x64, no cache restored                   | 6 min (582 crates)  | 23 min                              | about 29 min |
| Windows x64, partial restore                   | under 1 min         | 42 min                              | about 42 min |
| macOS arm64, run 42542822659, full cache match | 2.5 min (58 crates) | 107 min                             | 109 min 51 s |

Three conclusions follow directly. First, dependencies are cheap; the cache can save at most 5 to 7 minutes per row. Second, the cached macOS run (110 min) was slower than the uncached one (88 min), so run-to-run variance on the macOS runner is larger than the cache effect. Third, Linux compiles the same sources in about a quarter of the macOS time, which points at the runner and the symbol work rather than at the code. After `Finished`, the symbol dump took 27 s and bundling 30 s, so dumping symbols is not where time goes; producing the binary and its debug info is.

The step's duration history shows the symbol profile's effect. Before symbols (2026-11-04) macOS arm64 ran 37-40 min and macOS x64 47-57 min; with symbols on (11-06 to 11-07) they ran 75-79 and 81-92; the worst day (11-09) hit 111 and 101. Linux stayed at 25-28 min throughout. Windows did not move much (30-53 min).

The local build contradicts a simple "debug info is expensive" story. On the 12-core Mac a cold release build of `bibcode-desktop` took **1299 s with the shipped profile and 1260 s with the symbol profile**; the dSYM DWARF is 353 MB and no `dsymutil` or `ld` process showed up in a 15-second sampler. The same machine shows what dominates: `bibcode-server` lib 650 s, `bibcode-desktop` lib 187 s and the thin-LTO bin link 288 s, built one after another, so the build is serial for 17 of 21 minutes. Setting `codegen-units=16` on the symbol profile cut the total to **673 s**, about half. Peak memory per `rustc` was 8.7 GB for `bibcode-server` at the shipped profile and 12.0 GB at 16 codegen units. GitHub's macOS arm64 runner has 7 GB ([GitHub docs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)); Linux and Windows have 16 GB. The shipped-profile compile already needs more RAM than the macOS arm64 runner offers, so it is plausible that the runner swaps, but no run has measured paging, and the local symbol-profile memory at codegen-units=1 was not recorded. That gap matters for choosing the fix.

Windows arm64 shows a different waste. In one 103-minute job, `bibcode-server` was compiled five times by test and check steps (10 min 41 s, 5 min 06 s, 6 min 42 s, 17 min 30 s, 16 s) plus once more in the 36 min 15 s release bundle. That is 76 minutes of compiling one crate against about 2 minutes of tests.

Two side findings do not drive build time. `dump_syms` 2.3.9 logs `CfiError { kind: BadDebugInfo }` in 7 of 24 macOS job logs and never on Linux or Windows, yet exits 0 and the crash smoke job still passes its `trust == "cfi"` check; locally, six runs gave byte-identical output without the error. The flaky Windows arm64 test fails the first four of ten tests at exactly 10 s each, which looks like a timeout hit while the box is busy.

## The cache is thrashing, but fixing it buys minutes, not hours

GitHub's per-repository cache limit is **10 GB by default**, and entries unused for 7 days are removed. When the limit is exceeded GitHub saves the new entry first, then evicts oldest-accessed entries until usage is under the limit, and the docs call the resulting churn "cache thrashing" ([GitHub docs](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)). Eviction moved from every 24 hours to hourly ([GitHub changelog](https://github.blog/changelog/2025-09-29-new-date-for-enforcement-of-cache-eviction-policy/)), and the changelog itself warned of more thrashing. The measured store (9.98 GiB, six `native-desktop` entries of 1.5 to 1.85 GiB each wanted but three present, six pnpm entries of about 0.48 GiB, one of them from a pull request ref) fits that loop. Each lock-hash change on `main` writes a fresh 1.5-1.85 GiB entry per OS and architecture and evicts a live one.

The limit can now be raised. A November 2025 changelog made size and retention configurable, with usage above 10 GB billed at **$0.07 per GiB-month** and a budget control that turns the cache read-only at the cap ([changelog](https://github.blog/changelog/2025-11-20-github-actions-cache-size-can-now-exceed-10-gb-per-repository/), [billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). The REST endpoints are `PUT /repos/{owner}/{repo}/actions/cache/storage-limit` and `.../retention-limit` ([REST docs](https://docs.github.com/en/rest/actions/cache)). By that arithmetic, covering the 17 GB demand costs roughly 7 x $0.07, about **$0.50 per month**; that figure is my calculation, not a quoted price. What could not be verified: whether a public repository on a free plan may raise the limit at all (the changelog mentions Pro, Team or Enterprise), and the API's maximum values. The cheapest test is to call the PUT and read the answer.

Free ways to shrink demand come first. A pull request run can only save to its own merge ref, readable by its own re-runs only, yet those entries count against the same total ([GitHub docs](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)). Saving only from `push` on `main` removes them; `Swatinem/rust-cache` has `save-if` for this, while `actions/setup-node` has no restore-only switch in the README I read, so the pnpm store needs `actions/cache/restore` plus a save step gated on `push` (an inference from the missing input). Rust-cache is well suited to shrinking further because its cleanup keeps only dependency artifacts: it deletes `incremental/`, drops workspace crates unless `cache-workspace-crates` is set, prunes the registry to used crates and strips old files ([rust-cache README](https://raw.githubusercontent.com/Swatinem/rust-cache/master/README.md), [cleanup.ts](https://raw.githubusercontent.com/Swatinem/rust-cache/master/src/cleanup.ts)). Its key is two 8-hex hashes: an environment hash (rustc version, installed toolchains, and any `CARGO*`, `RUST*`, `CC*`, `CXX*`, `CFLAGS`, `CMAKE*` variable) and a manifest hash (Cargo.toml files with local versions zeroed, registry and git entries of `Cargo.lock`, `.cargo/config.toml`, toolchain files) ([config.ts](https://raw.githubusercontent.com/Swatinem/rust-cache/master/src/config.ts)). Only one restore-key is passed, the environment hash alone, so a lockfile change restores the newest sibling entry and saves a new one ([restore.ts](https://raw.githubusercontent.com/Swatinem/rust-cache/master/src/restore.ts)). Two consequences: a job that builds debug and release in one key stores both dependency sets in one entry (an inference from the pruning rule), and any CI-only `CARGO_PROFILE_*` environment variable changes the environment hash and so forfeits restores. Splitting the `key` per profile and dropping `cache-bin` are untested but low-risk size levers. Cargo also hashes the whole profile into every unit's fingerprint, so a symbol-profile build cannot reuse dependency artifacts built with different `debug`, `strip` or `split-debuginfo` settings ([Cargo fingerprint source](https://doc.rust-lang.org/nightly/nightly-rustc/src/cargo/compiler/fingerprint/mod.rs.html)); whether `strip` is part of that hash was not verified.

The external research agrees with the measurement on one point and cannot settle another. Rust-cache never stores the workspace crates by default, which matches the 80-97% figure. Whether `cache-workspace-crates: true` helps is unverified, and a rust-cache pull request notes that it grows entry count because source edits make new keys ([PR 349](https://github.com/Swatinem/rust-cache/pull/349)). sccache is the other route to caching first-party crates, but it cannot cache anything that invokes the linker (bins, dylibs, proc-macros), needs incremental compilation off ([sccache Rust.md](https://raw.githubusercontent.com/mozilla/sccache/main/docs/Rust.md)), and Depot measured it making release builds up to 50% slower while helping test builds 11-14% ([Depot](https://depot.dev/blog/guide-to-faster-rust-builds-in-ci.md)). Its GitHub backend draws on the same 10 GB pool, and no source covers sccache with thin LTO and one codegen unit. Third-party cache backends (S3 or R2 with sccache, or Blacksmith, RunsOn, WarpBuild caches) exist but most require their own runners, and I found no free drop-in for GitHub-hosted runners; their prices come from vendor and comparison pages and were not verified.

## One crate, one core, and a debug-info build on a 3-core runner

The measured local data and the external sources agree that `codegen-units=1` is the main compile-time lever. With one codegen unit the crate is a single LLVM module, so the parallel LLVM stage has nothing to fan out; rustc's own docs say 1 "may improve the performance of generated code, but may be slower to compile" ([rustc book](https://doc.rust-lang.org/rustc/codegen-options/index.html)), and a measured debug build of one crate took 9.7 s with one unit against 4.5 s with up to 16 ([Nethercote](https://nnethercote.github.io/2023/07/11/back-end-parallelism-in-the-rust-compiler.html)). Here the local ratio was 1260 s to 673 s, about 1.9x, on a loaded 12-core machine; on a 3-vCPU runner the idle cores are the same, and the compile is single-thread bound for the biggest crates. A ruff measurement quoted in a commit view gave thin LTO plus 16 units at 16 s against 41 s for thin LTO alone ([ruff commit](https://app.semanticdiff.com/gh/astral-sh/ruff/commit/3ce145c47669645c9031ec42ef9b339835e548c9)), a secondary source I could not verify independently. The price is runtime speed and code size; no 2024-2026 benchmark of thin LTO with 1 versus 16 units was found, so the cost to the shipped app must be measured, not assumed.

Where the external research disagrees with the CI history is debug info. The local build says the symbol profile is free (1260 s against 1299 s), yet macOS CI doubled when it was enabled. No source apportions debug-info cost between rustc, LTO and linking, and none measured `line-tables-only` against `debug=0`. The ThinLTO-with-debug-metadata cost is a hypothesis, not evidence. The better-supported candidate is memory: line-tables-only adds `.debug_info`, `.debug_abbrev`, `.debug_str` and `.debug_aranges` ([rust-lang/rust#109808](https://github.com/rust-lang/rust/pull/109808), via search summary), which raises rustc's resident size, and a 7 GB machine that is already short at 8.7 GB peak has no headroom. That would explain why Linux and Windows (16 GB) were unaffected and the 16 GB, 4-vCPU macOS Intel runner is the only other macOS data point. The 2026 doubling is therefore a hypothesis that one cheap experiment can test: log peak RSS and swap on a macOS arm64 run.

For packed dSYMs the evidence is weaker locally than the folklore suggests. `split-debuginfo=packed` runs `dsymutil` after link; one 2021 Cargo debug build spent about 7 of 10 s there ([internals](https://internals.rust-lang.org/t/help-test-faster-incremental-debug-macos-builds-on-nightly/14016)), and a 2025-26 LLVM thread timed classic `dsymutil` at 1:38 wall and 143% CPU against 45 s wall with `--linker=parallel` ([LLVM discourse](https://discourse.llvm.org/t/llvm-dsymutil-performance/89051)). That is a C++ link, and the 353 MB local dSYM finished in under a minute, so on the 3-core runner `dsymutil` is likely tens of seconds to a few minutes, not tens of minutes (inference). Cargo's own default on macOS is `unpacked`, so `packed` is an explicit choice. Cheaper routes to Breakpad symbols all lack proof: `dump_syms` documents DWARF in ELF and standalone PDB inputs and says nothing about debug-map inputs ([dump_syms](https://github.com/mozilla/dump_syms)), so `unpacked` still needs `dsymutil` before dumping (inference). Running `dsymutil` only on the shipped binaries rather than on every bin and test target, or adopting its parallel linker when the Xcode on the runner has it, is plausible; whether Xcode ships it was not found. Debug info for first-party crates only (`[profile.release.package."*"] debug = false`) is supported and leaves dependencies without line info but with function names and unwind data ([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)); it also keeps the dependency cache profile-identical only if both builds set it. A known `ThinLTO` plus `packed` bug ([rust-lang/rust#132677](https://github.com/rust-lang/rust/issues/132677), status unchecked) is worth a glance. The macOS-only `CfiError` has no documented cause; it matters only if symbol quality degrades, and the local evidence says output is complete.

## Ranked fixes for Windows and macOS runners

The ranking weighs saved time against effort, starting with what the measurements prove.

1. **Compile each crate once per Windows job (saves up to about 40 min on the Windows arm64 row, low effort).** The six compiles of `bibcode-server` come from separate `cargo check --all-targets`, `cargo test -p`, `--lib` and `--test` invocations plus the release build. The release profile cannot be shared with the test builds, but `check` is metadata-only and not reused by `cargo test` ([cargo check docs](https://doc.rust-lang.org/cargo/commands/cargo-check.html)), so replace it with `cargo test --no-run` (or `cargo nextest archive`) once, then run the three selections from that build ([nextest](https://nexte.st/book/reusing-builds)). Alternating `-p` and `--workspace` can also change the unified feature set and recompile dependencies ([Cargo features](https://doc.rust-lang.org/cargo/reference/features.html)); identical package and feature selection, or a `cargo-hakari` workspace-hack, prevents it. The fixed `-j 2` on a 4-vCPU Windows runner halves compile parallelism ([Cargo config](https://doc.rust-lang.org/cargo/reference/config.html)); the 17 min 30 s `--lib` build is the first thing to retest without it. That the cargo selections truly rebuild is inferred from the timings, which show build times of minutes against 16 s for the last step; confirm with `cargo ... -v`.
2. **Stop the cache thrashing (saves 5-7 min per row and removes variance, low effort, about $0.50 per month if billed).** Save only on `push` to `main`, drop PR-ref pnpm saves, and try raising the limit by API.
3. **Take the symbol build off the 7 GB macOS arm64 runner or measure memory first (potentially 35-40 of 80 min, medium effort).** Options: run the symbol bundle only on tag or release workflows; use a larger runner (GitHub larger macOS runners cost about $0.102 per minute for the M2 Pro tier, third-party M4 about $0.08 ([compiler.dev](https://compiler.dev/guides/faster-github-actions-runners)), prices not verified against vendors); or build the macOS arm64 symbols on the 14 GB Intel runner, supported until about 2027 by unofficial sources. Log peak RSS first, because without it the cause remains a hypothesis.
4. **Raise `codegen-units` in the symbol or PR profile (halves compile in the local test, medium effort).** The local result (673 s against 1260 s) is the strongest speed evidence, but memory rises to 12 GB at `bibcode-server`, which will not fit the 7 GB runner. Use it on Linux and Windows 16 GB rows, or on PR builds only, and keep `codegen-units=1` for the shipped binary after measuring the runtime cost. Setting it by `CARGO_PROFILE_RELEASE_CODEGEN_UNITS` also changes the rust-cache environment hash.
5. **Windows file-system tuning (uncertain, one-line try).** Moving TEMP to D: cut a pip suite 10-28% on hosted Windows runners while ReFS Dev Drive saved little ([sichard.ca](http://sichard.ca/blog/2025/03/faster-pip-ci-on-windows-d-drive)); Rust numbers do not exist, and `cargo` process spawning is slow on Windows ([nextest](https://nexte.st/docs/design/why-process-per-test/)). Put `CARGO_TARGET_DIR`, TEMP and `CARGO_HOME` on D: and measure.
6. **Dev and test profile tweaks.** `debug="line-tables-only"` or `0` for dev and test, `CARGO_INCREMENTAL=0` ([corrode](https://corrode.dev/blog/tips-for-faster-ci-builds/)), and `[profile.dev.package."*"] debug = 0` shrink targets and caches. Gains were not sourced as numbers. `-Z threads` and Cranelift were still nightly-only in the 2026 project goals ([Rust goals](https://rust-lang.github.io/rust-project-goals/2026/parallel-front-end.html)) and are not options for stable 1.98. Linker swaps do not apply: lld is default only on x86_64 Linux ([Rust 1.90](https://blog.rust-lang.org/2025/09/18/Rust-1.90.0/)), the macOS and Windows alternatives were not benchmarked, and linking happens after the LTO phase that dominates ([Nethercote](https://nnethercote.github.io/2023/07/11/back-end-parallelism-in-the-rust-compiler.html)). Third-party runners (Linux 4 vCPU at $0.008 per minute on two vendors) have no Rust-specific numbers, and no Windows price was found.
7. **Flaky Windows arm64 test.** Wait for a child-emitted readiness marker before starting the timeout clock, answer ConPTY's startup query, and run the PTY test alone, which is how other projects fixed ConPTY flakes ([codex-rs](https://upd.dev/layers/codex/src/branch/main/codex-rs/utils/pty), [issue 36328](https://claudeissues.com/issue/36328-60s-startup-delay-in-conpty-da1-sentinel-never-receives-response)). Cheap, and not a build-time factor.

## Conclusion

The repository's measurements overturn the premise that a caching or backend change fixes slow builds: the cache is saturated, but removing it entirely would cost 5-7 minutes on rows that spend 80-110. The surviving explanations are structural: first-party code compiled repeatedly (five times on Windows arm64), one-thread-bound codegen with `codegen-units=1`, and a symbol build that doubles macOS time only on the smallest runner. The only unexplained gap is why the local symbol profile is free while CI is not, and a peak-memory log from a macOS arm64 run is the experiment that closes it; until then, treat the memory theory as the leading hypothesis and keep the first three fixes, which do not depend on it.

Unverified and unreconciled items: public-repo eligibility for paid cache limits; `cache-workspace-crates` and sccache effects on this workload; whether Xcode's `dsymutil` has the parallel linker; the `dump_syms` CFI error cause; all third-party pricing; the ruff and Phoronix claims (secondary views or snippets only).
