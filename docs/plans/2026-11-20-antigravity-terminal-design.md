# Antigravity terminal and chat: design (issue 399)

Status: reviewed 2026-11-20 by Codex (verdict "Needs rework") and the
advisor. All findings were processed (see "Review record"); the fixes were
checked by the advisor and not reviewed again by Codex. The revisions made
after those reviews (the live measurements and the plan review 3 alignment) are
not yet reviewed.

Scope. Issue 399 asks for an Antigravity AI Terminal that starts the `agy` TUI.
On 2026-11-20 the owner decided that the same pull request also builds an
Antigravity chat panel over `agy acp` (ACP v1, JSON-RPC over stdio), with no
SDK. That reverses spec R13 and D9. This note designs both modes. The
"Terminal only" section at the end lists what changes if the chat were dropped
again, so either answer stays possible.

Sources. The research report `research-antigravity.md` in
`docs/plans/2026-11-20-undo-remote-delete-antigravity/` (CLI 1.5.13, read on
2026-11-20), the source at commit `56573c19e`, and live measurements the
coordinator took on 2026-11-20 against an installed, signed-in `agy` 1.5.13
(two handshakes and one real turn; transcripts kept outside the repository).
No `agy` exists in CI or the labs, and no test spawns it.

## Decisions

Each decision names the alternative that lost and its trade-off.

### D-A1. Driver slug `antigravity`

The driver kind is `antigravity`, the default instance id is `antigravity`,
and the label is "Antigravity".

Lost: `agy`. It is the binary name, and the slug must not be used as the
executable (issue 399). A slug equal to the binary would hide a missing
special case in `default_provider_binary`. The editor catalog's id
`antigravity` (`packages/contracts/src/editor.ts`) is a separate namespace
(`EditorId`) and stays unchanged (R13, third bullet).

### D-A2. Disabled by default (spec D7)

`built_in_provider_defaults()` gains
`"antigravity": { "enabled": false, "binaryPath": "agy", "customModels": [] }`,
and `AntigravitySettings.enabled` decodes to `false`.

The inventory's synthesized roster in `provider_inventory::definitions` falls
back to `unwrap_or(true)` when settings carry no `enabled` value. Settings that
went through `apply_settings_defaults` always carry it, but raw settings (a
test's `json!({})`, `maintenance_target`, `instance_custom_models`) do not. The
roster therefore reads the fallback from `built_in_provider_defaults()`, the one
table both settings readers already use, so `definitions(&json!({}))` yields a
disabled Antigravity instance. A user-created instance under
`providerInstances` without `enabled` keeps the existing rule: it inherits the
legacy `providers.antigravity.enabled`, which merged settings set to `false`,
and only then `true`. Settings shows a missing `enabled` as enabled, so the
Settings task writes `enabled` explicitly when it creates an Antigravity
instance and tests that the card and the inventory agree.

Lost: enabled but unready, like Cursor. Every machine without `agy` would then
show an error card, and a user who never asked for Antigravity would see it in
pickers once `agy` exists on PATH for another reason (the IDE launcher clash
below).

Roster order. `antigravity` goes last in the roster loop, the exact-order test
and every built-in list, so it is the last built-in that a "first enabled"
fallback reaches. `definitions` lists configured `providerInstances` before
the roster, so a custom Antigravity instance the user created can come first;
that is the user's own choice, and with chat built it is a valid target.

### D-A3. Binary path and install probe

The binary path defaults to `agy`, never the slug: `default_provider_binary`
gains `"antigravity" => "agy"`, the settings schema uses
`makeBinaryPathSetting("agy")` with placeholder `agy`, and the legacy patch
validation accepts `providers.antigravity.binaryPath` as a string. The probe is
the existing generic one: `<binary> --version`, run only for an enabled
instance. A binary that cannot be started reads "not installed"; a `--version`
that exits non-zero reads installed with a warning (the existing behaviour at
`provider_inventory.rs` lines 731 to 742).

Lost: resolving every `agy` on PATH and keeping the one whose output looks like
the CLI (research recommendation). It needs a second probe format that no
source documents. The configured binary path and the documented check
(`agy --version`, and `command -v agy` or `where agy`) cover the clash.

### D-A4. Chat-only version check at launch: 1.5.4; no inventory gate

The inventory gates nothing, so the terminal is never disabled by the CLI
version. Issue 399's acceptance criterion (a machine with `agy` can open the
terminal) stays true for every version.

The chat driver checks the process it launched. The live `initialize` answer
carries the CLI version in `agentInfo.version` (measured on 1.5.13), so the
runtime reads the first `major.minor.patch` there and, below 1.5.4, closes the
connection before `session/new` with "Antigravity chat needs CLI 1.5.4 or
later; this one is <version>. Run `agy update`, then try again. The
Antigravity Terminal still works." A version with no `major.minor.patch`, or
none at all, is not gated. A CLI with no working `agy acp` (the child exits
before answering `initialize`, or `initialize` returns "method not found")
gets the same message without a version. The check runs on the launched
process, so a binary replaced after the last probe is still checked, and no
separate `--version` child is needed.

Why 1.5.4. Google's own changelog, read on 2026-11-20, says 1.5.0 added
`agy acp`, 1.5.1 fixed session close, reload and resume during a prompt, and
1.5.4 fixed ACP turns hanging when a tool call needed a second permission
approval and fixed sessions dropping back to the default mode on reload or
resume. Both 1.5.4 fixes are in paths this design uses (D-A5, D-A9).
BiBCode's compatibility at 1.5.4 is still unverified without a live run.

Lost: an inventory gate (1.5.2, Orca's value, or 1.5.4). With one readiness per
instance it would disable the terminal too, because the OpenCode precedent sets
`status = "error"` for the whole instance and the menu requires `ready` for
both actions. Lost too: a separate readiness per mode in the snapshot, which
needs a new `ServerProvider` field. The start-time refusal shows its specific
message in the thread, which is the one place the user sees it.

### D-A5. Permission flag

The terminal passes `--dangerously-skip-permissions` (spec D8), as the Claude,
Codex, Cursor and Grok terminals pass their bypass flags (the OpenCode terminal
passes none), and as Orca does by default. The provider guide names the flag
and what it does.

The chat does not pass it. The chat answers each `session/request_permission`
from the thread's runtime mode. In `full-access` it selects the `allow_once`
option, not `allow_always`, so a later switch to approval-required takes effect
on the next request; the shared `acp_mode::auto_approved_option_id` prefers
`allow_always`, so the Antigravity runtime picks the option itself. If no
`allow_once` option is offered, the request goes to the user. Outside full
access BiBCode never answers a permission request by itself, whatever the mode
(plan interaction mode included: measured on 1.5.13, `plan` ran a write tool
into the CLI's own data folder without asking, so it is not a read-only mode). A flag on `agy acp` would fix the policy for the process
and ignore a thread switched to approval-required later. Cancelling a turn
abandons pending requests (ACP page), so the runtime drops its pending
approvals on cancel, and an answer that arrives after cancel is discarded.

Modes. The CLI advertises `default` (ask before edits and commands),
`accept-edits`, `auto` and `plan`, both as `modes.availableModes` and as the
`mode` config option (measured). The runtime sets modes through the `mode`
config option by id and never through `acp_mode::resolve_requested_mode_id`,
whose fallback to the current or first non-plan mode would weaken approval:
`approval-required` sets `default`, `auto-accept-edits` sets `accept-edits`,
`full-access` sets `auto`, and plan interaction mode sets `plan`. For
approval-required the runtime waits for the acknowledgement of `default`
before the first prompt; a missing or rejected `default` refuses the start,
failing closed as `runtime_mode` does for an unknown mode (issue 376; owner
ruling, 2026-11-20). The same rule holds for every mode the runtime writes: an
unadvertised or unacknowledged `accept-edits`, `auto` or `plan` refuses too. When
a live switch is not acknowledged, the session keeps running, so the runtime
writes the mode again before the next prompt and refuses the prompt if that
fails. The whole start (handshake, session open, model and mode) is bounded by
60 seconds; a CLI that does not answer in time fails the start with a retryable
`StartTimedOut`. `session/set_config_option` answers with the full
`configOptions` list and emits `config_option_update` and
`current_mode_update` (measured). Actions the user's own Antigravity rules
allow still never prompt (ACP page); the provider guide states it.

Why not the flag for full access. `agy acp --help` lists
`--dangerously-skip-permissions` (measured), and the coordinator asked whether
passing it would be simpler. It is not kept, for one reason: the flag fixes the
policy for the whole process, and a thread's runtime mode can change while the
process runs (`option_application_method` "live" in `provider_runtime.rs`), so
a thread switched from full access to approval-required would keep
auto-approving until a restart. Answering each request costs one `allow_once`
reply, and Cursor's chat already works this way.

Lost for the terminal: no flag, so the TUI prompts (the research's first
advice). Lost for the chat: the flag on `agy acp`, for the reason above. Lost
for both: a per-agent permission setting, which no BiBCode terminal has; it
would be its own issue.

### D-A6. Model and effort

Catalog. The models and thinking levels come only from a session: the live
`session/new` answer carries `configOptions` with ids `model` (base model
values), `thought_level` (`low`, `medium`, `high`, `xhigh`) and `mode`, and
also `models.availableModels`, whose ids combine model and effort (measured on
1.5.13). The slow inventory probe of an enabled instance therefore starts
`agy acp`, sends `initialize`, then `session/new` with the probe directory,
reads the options, and sends `session/close` (advertised as
`sessionCapabilities.close`). The parser prefers `configOptions`: `model` maps
to BiBCode's model and `thought_level` to its effort. It falls back to
`models.availableModels` only when `configOptions` has no `model`. An empty or
unknown answer keeps the instance's custom models, so a parse failure never
blocks the chat. A `-32000` answer whose message is
`Authentication required` sets `auth.status = "unauthenticated"` and the
sign-in message, but leaves `status` at `ready`: the menu requires `ready` for
both actions, and the terminal is where the user signs in. The chat start then
returns the D-A8 sign-in error. The quick probe is unchanged: like every driver
except OpenCode, it reads ready once the executable resolves.

Retention. `merge_provider_snapshot` in `control.rs` already keeps the last
models when a refresh is not a rich one, for the same instance id and driver
(`provider_snapshot_identity`; the binary path is not part of the identity). C3
extends it, for the `antigravity` driver only, to keep the last `auth` the same
way when the refreshed snapshot's auth is `unknown`. Other drivers keep their
current behaviour. A changed binary path is not detected by the merge, so the
old auth shows until the next full probe replaces it; a successful full probe
after sign-in replaces it too.

Frequency. A full probe runs on a client subscription, on a settings change and
on the background check (`FullProviderRefreshTrigger` in `control.rs`). Each
full probe of an enabled Antigravity instance creates and closes one session in
the user's account.

This is new behaviour. The Cursor probe asks `cursor/list_available_models`
and creates no session. The Antigravity probe creates and closes one empty
session per slow probe in the user's account, and it runs the official
unmodified `agy acp` with the user's own sign-in (D-A15). The provider guide
states it.

Lost: `agy models`. Its output format is not published, and it gives no sign-in
signal. Lost too: no inventory catalog, with the models read only from the
first real chat session. No path exists for a driver to publish models back
into the inventory (`PublishedProviderInventory` is read by the factory, not
written by drivers), so the model picker would stay empty.

Model and effort contract (shared by the runtime, the inventory and the
terminal). The existing ACP option parser publishes the `thought_level`
category under the BiBCode option id `reasoning` (`provider/cursor/model.rs`
near line 505), so `reasoning` is the BiBCode id for the thinking level, and
the runtime writes it back with `configId` `thought_level`. The model is
written with `configId` `model` and the unsuffixed value the catalog
advertised. Every write is `session/set_config_option` with
`{ sessionId, configId, value }`; an unknown value fails with `-32602`
(measured). When only `models.availableModels` exists, the suffixed model ids
are sent unchanged through `session/set_model`, which no live run has
exercised. The Cursor setter, which expects fixed wire ids, is not reused.
Because the thinking levels depend on the model (measured), the runtime writes
the model first, re-reads `configOptions` from the answer and from each
`config_option_update`, and only then writes the thinking level; a level the
new model does not list is rejected with the existing error. For the same
reason the inventory catalog carries the thinking levels per model (each model
entry has its own `reasoning` option list and default), never one global
effort list. The runtime reads the ACP fields of a tool call (`toolCallId`,
`kind`, `title`, `locations`, `rawInput`) and ignores the non-standard `name`
and `args`. Permission request ids are kept as the JSON value received, because
the CLI sends string ids. An option the session does
not advertise is rejected with the existing "unsupported option" error, and
one failed option does not undo the others. The shared `auto` model sentinel
is stripped before any send, as the server already does for other drivers.

Terminal. `--model` and `--effort` come only from the raw
`settings.providerSessionDefaults.antigravity` value: `model`, and the
option with id `reasoning` (one of `PROVIDER_EFFORT_OPTION_IDS`). The resolver's fallback
never adds them. R12 passes the flags only when session defaults supply them,
and that holds with a catalog too. Without a configured default, the TUI starts
on its own default model.

One stored default for both modes (owner ruling, 2026-11-20; R12 as
written). The session-defaults control stores the `configOptions` `model`
value and the `thought_level` value. The live `model` values have no effort
suffix and look like CLI `--model` slugs, and the `thought_level` values are
lower case like the CLI's `--effort` levels (observed on 1.5.13, not proven by
a TUI launch). The terminal passes both as stored. If the CLI rejects a value,
the TUI prints its own error in the terminal, which the user sees and fixes by
changing the default.

Settings card. The card shows the binary path and the shared session-defaults
control for the default instance. With a catalog, the control offers the
advertised models and, when present, the thinking level. Without one, it
offers custom models only and no effort.

Lost: a free-text model and effort field on the card. It is new UI with no
validation source.

### D-A7. Reuse of the Cursor ACP code

The transport is reused as it is. `provider::cursor::acp`
(`AcpJsonRpcConnection`, line bounds, error classes, `acp_turn_state`) already
serves Grok through a re-export in `provider/grok/mod.rs`. A new
`provider/antigravity/` module re-exports it the same way and adds its own
`runtime.rs`, modeled on `cursor/runtime.rs` for the standard ACP v1 methods:
`initialize`, `session/new`, `session/load`, `session/prompt`,
`session/cancel`, `session/set_mode`, `session/set_config_option`,
`session/request_permission` and `session/update`. It drops the Cursor
extensions (`cursor/ask_question`, `cursor/create_plan`, `cursor/update_todos`)
and `authenticate`. The docs say questions use ACP elicitation forms in
clients that support them. BiBCode's ACP client advertises no elicitation
capability, so the first version handles no questions; any unknown request is
answered with JSON-RPC "method not found" and logged by method name only.
Elicitation support is a follow-up.

Lost, option 2: move `cursor/acp.rs` to `provider/acp/` first. It is a rename
across Cursor, Grok and the inventory imports with no behaviour change, so it
belongs in its own change. Lost, option 3: generalize `CursorSessionRuntime`
into a dialect (provider name, auth method, extension table). Antigravity's
real wire format is unverified, so coupling the shipped Cursor chat to guesses
about `agy` risks a Cursor regression; a second implementation keeps the risk
in the new driver. If the third ACP runtime turns out close to Cursor's after
real use, the dialect refactor becomes the follow-up.

### D-A8. Chat launch and authentication

Launch. The driver spawns `<binary> acp` through `spawn_child`, with the
thread checkout as working directory and the environment that
`provider_launch_environment` builds: the instance's provider environment,
plus the open-URL session's variables when one is configured, as for every
provider. It adds no flag (D-A5) and no variable of its own. `mcpServers` is
sent empty (D-A9).

Handshake. The runtime sends `initialize` with protocol version 1 and the same
client capabilities as Cursor (no file system, no terminal). It refuses a
response whose `protocolVersion` is not 1, with the D-A4 message, and it reads
`agentCapabilities` for `loadSession` and the session capabilities (resume,
close) that D-A9 uses. Cursor ignores the initialize result
(`cursor/runtime.rs`), so this check is new.

Authentication. BiBCode never signs the user in, never reads Google
credentials or keyring entries, and offers no ACP auth method id. It does not
call `authenticate`, because the research reports that `authenticate` can open
a browser even with a valid token (upstream issue 1637). The CLI's cached sign-in
from an interactive `agy` or `agy acp --login` is used. An error with code
`-32000` and the message `Authentication required` becomes
`ProviderRuntimeError::Provider` with the message "Antigravity is not signed
in. Open an Antigravity Terminal and run `agy`, or run `agy acp --login`, then
send the message again." Code `-32000` is a generic JSON-RPC server error, so
any other `-32000` message passes through unchanged. The sign-in error and the
D-A4 version error are final for that start: the durable launch path must not
retry them, they appear in the thread once, no prompt is written, and the
terminal stays available.

Lost: offering `terminal-login` or `oauth-personal` through `authenticate`. Both
start a sign-in BiBCode would have to drive.

### D-A9. Sessions and resume

The ACP `sessionId` is the resume token, stored in the turn's resume cursor as
for Cursor (`provider_runtime.rs` `cursor_field` `"sessionId"`). After a server
restart the driver reopens the saved session. It prefers `session/resume` when
the initialize result advertises it under
`agentCapabilities.sessionCapabilities.resume` (ACP spec; the Antigravity ACP
page says resuming does not replay history). CLI 1.5.13 advertises `resume`,
`close`, `load` and `list`, each also under a snake-case
`session_capabilities` key (measured); the runtime reads the camel-case keys
and falls back to the snake-case ones. Otherwise, when `loadSession` is
advertised, it calls
`session/load` with `sessionId`, the checkout `cwd` and the empty `mcpServers`
the ACP spec requires (Cursor sends only `sessionId`). The ACP spec lets load
replay history as `session/update` notifications, so the runtime drops every
update that arrives before the reopen call returns, and every update whose
`sessionId` is not the open session's. BiBCode's own projected transcript stays
the record the user sees; the agent keeps its server-side context. If neither
capability is advertised, the driver starts `session/new`.

Load cannot detect a lost conversation: `session/load` of an unknown id
succeeds and returns a session with that id (measured on 1.5.13). Resume is
therefore tried first, and its `-32603` "Failed to read session" answer is the
missing-session signal (measured); `session/resume` of a closed session from a
new process succeeds with no replayed update (measured). On that signal the
driver starts `session/new` and returns the new id. The runtime treats a
returned id that differs from the requested one as a lost resume
(`resume_lost` in `provider_runtime.rs`, near line 9830). For an ordinary turn
that sets the context handoff for the next turn. `FrozenConversationLost` is
raised only when the launch asks to abort on a lost resume
(`abort_on_lost_resume`) for a frozen delivery; other frozen deliveries are
released by `release_frozen_delivery` (checked against the `resume_lost` code in
`provider_runtime.rs` on 2026-11-21: it matches). Any other reopen error is transient and
keeps the saved id. Load is used only when resume is not advertised, and then
a lost conversation is not detectable. C1 tests pin
resume, load, neither capability, a replayed update, a stale-session update, a
transient failure, a sign-in failure, and a missing session; C2 tests a missing
session with an ordinary and a frozen delivery.

Not supported in the first version:

- `session/list`, because it can return desktop-app sessions that then fail.
- Forks and conversation rewind: `supports_conversation_rewind` stays false,
  and checkpoint rollback returns the existing `unsupported` error.
- Turn steering and compaction.
- MCP passing. `mcpServers` is empty, so BiBCode's MCP tools are not offered to
  Antigravity. HTTP MCP servers need `--process-per-session`, whose effect on
  session load is unverified.
- Images beyond what the shared attachment path already does. Attachments go
  through `AttachmentMaterializer` and `append_file_references` as text file
  references, as for Cursor.

### D-A10. Known ACP bugs and their effect

- Provider and quota errors end a prompt with `end_turn` and the error only as
  text (upstream 1570). The first version shows that text as the reply and
  marks the turn completed. Scanning message text for errors is left out,
  because the wording is not documented. A C1 fixture pins this limitation.
- `session/list` returning foreign sessions (D-A9) does not apply, because the
  client never calls it.
- A subagent's `run_command` can time out without a permission request
  (upstream 1658). BiBCode can only answer requests the agent sends, so in any
  mode such a command can fail inside the agent. The provider guide states it.
- A session can wedge after a question plus load (upstream 1581): later prompts
  return at once with an empty `end_turn`. The first version answers no
  questions (D-A7), which avoids the trigger it can see. Two cases are kept
  apart. An unanswered cancel: after `session/cancel`, if the prompt response
  does not arrive within a bounded wait (10 seconds), the runtime ends the turn
  as cancelled and signals the driver, which stops the child as a requested
  stop (not a `subprocess.crash`); the next turn starts a new process and
  reopens the session. Measured on 1.5.13, the CLI answers a cancel at once, so
  this path is a guard against the upstream wedge.
- The shared transport ends the connection on a stdout line over 128 KiB, and
  the CLI repeats a written file's content in the non-standard `args` of every
  `tool_call` and `tool_call_update`. Writing a large file can therefore end
  the session with a line-too-long error. The provider guide should state it. A completed empty reply is shown as an empty reply; the user's
  recovery is a new thread, which starts `session/new`. The existing idle
  timer does not help here, because it waits for a confirmed idle session.
  C1 tests both cases.

### D-A11. Process supervision and Profiler coverage

- The chat child spawns through `spawn_child`, whose
  `spawn_child_after_spawn` applies `configure_supervised_background_command_wrap`
  and calls `attribution.register_identity` on the spawned process (read in
  `provider_runtime.rs`). An unrequested exit reaches
  `exits::report_exit(Watch::Failures, ...)` with `kind: "provider"` in the
  shared session pump (near line 12227), which every driver feeds through
  `exited_process`, so it becomes a `subprocess.crash`.
- The D-A4 version check reads `initialize`, so it starts no extra child.
- A start that fails during the version check, `initialize` or the session
  open goes through the existing startup-failure shutdown, which kills and
  reaps the child; `report_exit` covers exits after the session pump starts,
  as for every driver. C2 tests an inert child that exits during `initialize`.
- The inventory probe spawns through `supervised_command` and
  `stop_supervised_child`, as the Cursor probe does. The Cursor probe does not
  register attribution; the Antigravity probe should not copy that gap, so C3
  registers its child with `register_identity` if the inventory has the
  registry, and otherwise records the gap for both probes as a follow-up.
- No RPC method is added. Chat uses the existing orchestration methods, so
  `is_long_running` needs no entry.
- `tracing` logs and Profiler records carry the method name, error code and
  class only, never prompt, message, option values, provider stderr or
  terminal content. Provider error text reaches the user only through the
  thread's error message, as for Cursor, and never a log line; C1 tests this
  with a synthetic secret marker in an error and in stderr.

### D-A12. Server dispatch

`canonical_provider_kind` gains `"antigravity"`; `provider_binary_settings`
reads `providers.antigravity`; `native_adapter_key` returns `antigravity-acp`;
the driver factory gains an `AntigravityDriver`; `cursor_field` treats it as
`sessionId`; the ACP line-too-long classifier and its test table include it,
as does the adapter-key test table. Delivery follows `CursorDriver::deliver`,
the production mapping: a write that failed before sending is
`DefinitelyNotSent`, a remote JSON-RPC rejection is `Rejected`, any other
failure after the write is `Ambiguous`, and a completed prompt is `Accepted`.
Restart recovery already treats a provider without a delivery lookup as
uncertain (`turn_delivery.rs`), so a sent prompt is never replayed
automatically. The `delivery_outcome` table at `turn_delivery.rs` line 1991 is
test-only and gets no entry. `orchestration_rpc.rs` reaches the driver through
`canonical_provider_kind`, so it needs no edit. Code review offers every chat
action as a reviewer (`codeReviewerActions` in `codeReview.ts`), so an
Antigravity chat becomes a reviewer choice with no edit; no review terminal is
added.

### D-A13. Display name

`provider_display_name("antigravity")` returns "Antigravity", and contracts'
`PROVIDER_DISPLAY_NAMES` gains the same entry, so the snapshot's `displayName`
is "Antigravity" and the existing parity test
`provider_display_names_match_the_contracts_table` keeps them equal.

### D-A14. First-run prompts and the PATH clash

The TUI's first launch asks for a colour scheme, a rendering mode and
workspace trust inside the embedded terminal. BiBCode does not answer them and
does not write workspace trust (Orca does; BiBCode never edits Antigravity's
settings files). Google documents these prompts for the TUI only; whether a
workspace never opened in the TUI affects `agy acp` (for example through
workspace trust) is unverified. The provider guide states that the first
terminal run per workspace is interactive and suggests opening the terminal
once before the first chat.

The IDE once shipped a launcher also named `agy`; newer IDE releases are
reported to install `agy-ide` and `antigravity-ide`. If an old launcher is
first on PATH, both the terminal and the chat run the wrong program. The
`--version` probe cannot tell them apart: a launcher that exits 0 reads ready.
The chat start then fails at `initialize` with the D-A4 message, and the
terminal shows whatever the launcher does. The fix is an absolute binary path
in Settings, and the guide shows how to check which `agy` is found
(`command -v agy` or `where agy`, then `agy --version`).

### D-A15. Google's terms

The research reports that Google's FAQ says third-party tools wrapping `agy`
are not supported on consumer plans, while a forum reply written on Google's
behalf says the unmodified official ACP server is supported for single-user
interactive development. Whether a distributed desktop app counts is not
established. The terminal runs the user's own unmodified CLI interactively.
The chat runs the unmodified official `agy acp` with the user's own sign-in,
and never proxies tokens, rotates accounts or wraps `agy -p`. The provider
guide must say that the position is unresolved, link the terms and the FAQ,
and name an API key or an enterprise plan as the officially supported route.
The research's advice to get a written answer from Google before shipping chat
publicly is an open decision for the owner.
