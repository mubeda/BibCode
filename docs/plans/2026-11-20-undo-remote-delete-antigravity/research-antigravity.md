# Launching Antigravity now, wrapping ACP later

Launch Google's Antigravity CLI (`agy`) as an AI Terminal now, and build the chat-panel provider later on `agy acp` rather than on any SDK. The terminal path is low-risk: `agy` is a self-contained Go binary installed by a curl or PowerShell script, so BiBCode needs no Node or Python and only has to spawn it in a PTY with the project as the working directory ([Getting started](https://antigravity.google/docs/getting-started?tab=cli)). The chat path has a clear transport, `agy acp`, an official ACP v1 server over stdio shipped in CLI 1.5.0 ([ACP page](https://antigravity.google/docs/cli/acp.md)). Neither route fits the official SDK, which is a Python package (`google-antigravity`, Alpha, version 0.1.24) that bundles a compiled runtime and has no Rust or TypeScript counterpart ([PyPI](https://pypi.org/project/google-antigravity/)). The two real risks are not technical. First, Google's terms and FAQ forbid third-party tools from accessing Antigravity on consumer plans, and no Google text clearly approves BiBCode's use ([FAQ](https://antigravity.google/docs/faq)). Second, ACP is about 16 days old with many open bugs ([issue list](https://github.com/google-antigravity/antigravity-cli/issues?q=acp)). Most observation signals (hooks, status line) require editing the user's own config files, so the terminal integration should stay a plain launcher at first. Most evidence below comes from docs read through a summarizing fetch tool, so exact flag spellings should be re-checked against `agy --help` before they ship. Nothing was installed or run.

## One binary name, two install paths

The CLI installs with `curl -fsSL https://antigravity.google/cli/install.sh | bash` on macOS and Linux, placing `agy` in `~/.local/bin`. On Windows it uses `irm https://antigravity.google/cli/install.ps1 | iex` in PowerShell or an `install.cmd` script, which installs `agy.exe` ([Getting started](https://antigravity.google/docs/getting-started?tab=cli)). The official docs put the Windows directory at `%LOCALAPPDATA%\agy\bin` ([Troubleshooting](https://antigravity.google/docs/cli/troubleshooting)). A third-party guide reports `%LOCALAPPDATA%\Antigravity\agy.exe` ([guide](https://pasqualepillitteri.it/en/news/3422/antigravity-cli-agy-install-migrate-gemini-cli)). The same guide mentions a compatibility alias `antigravity-cli.cmd`, which no official source confirms. No official npm, Homebrew or winget package for the CLI was confirmed. A search summary attributed winget to the Flutter docs, but the page itself did not contain it. The installer accepts `--skip-path` and `--skip-aliases` (it otherwise purges legacy `agy` and `antigravity` shell aliases) ([Authenticate docs](https://antigravity.google/docs/install?tab=cli)). The CLI self-updates (`agy update`), and `AGY_CLI_DISABLE_AUTO_UPDATE=true` turns that off ([Troubleshooting](https://antigravity.google/docs/cli/troubleshooting)). One issue reports the background updater renaming `~/.local/bin/agy` mid-session ([#1670](https://github.com/google-antigravity/antigravity-cli/issues)). Releases are near-daily, with 1.5.13 on 2026-11-19 the latest seen ([releases](https://api.github.com/repos/google-antigravity/antigravity-cli/releases?per_page=5)).

The name clash is real but only partly documented. The Antigravity IDE historically shipped a launcher also called `agy`. A Gemini CLI issue shows distributions shipping `antigravity` without `agy` ([gemini-cli#15553](https://github.com/google-gemini/gemini-cli/issues/15553)), and a Firebase Tools change moved IDE detection from `agy` to `antigravity` ([PR 10063](https://github.com/firebase/firebase-tools/pull/10063)). A Google codelab snippet mentions an "agy-ide command line tool", which suggests the IDE launcher was renamed, but that is a single snippet and no version is confirmed ([codelab](https://codelabs.developers.google.com/getting-started-agy-ide)). A third-party guide describes a Homebrew `antigravity` formula installing `antigravity` into `/opt/homebrew/bin` and the CLI installing `agy` into `~/.local/bin`, with PATH order deciding which `agy` wins. Practically, BiBCode must not trust the name. It should resolve every `agy` candidate on PATH plus the documented install locations, run `agy --version` on each (the safe probe; `agy version` can fail without a TTY per a community source), and accept only the one whose output looks like the CLI. It should also run `agy --help` once to confirm the expected flags exist. This also lets a user point BiBCode at an absolute path, which the ACP docs recommend for editors because GUI processes often have a thinner PATH than a shell.

## The launch command and what the first run asks

The flags below come from the official CLI reference ([reference](https://antigravity.google/docs/cli/reference)). Running `agy` with no subcommand starts the interactive TUI in the current directory.

| Flag                              | Meaning and version notes                                                                                                                                                                                |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--version`                       | Verifies the install; the probe BiBCode should run.                                                                                                                                                      |
| `--model <slug>`                  | Slugs come from `agy models`; the full list is not published. Gemini 4 Neon was added in 1.5.13.                                                                                                         |
| `--effort`                        | "low through max (depends on model)"; an older cheat sheet (1.2.4) listed only low, medium, high.                                                                                                        |
| `--mode accept-edits\|auto\|plan` | `auto` needs 1.3.5+ on macOS and Linux and 1.4.4+ on Windows. Since 1.5.7 the default agent mode is Auto.                                                                                                |
| `-c`, `--continue`                | Resume the most recent conversation. It reads `~/.gemini/antigravity-cli/cache/last_conversations.json`, keyed by workspace path ([Resume doc](https://antigravity.google/docs/cli/commands/resume.md)). |
| `--conversation <id>`             | Resume a specific conversation. Stable, unlike `-c`, which can pick another terminal's session.                                                                                                          |
| `--dangerously-skip-permissions`  | Auto-approves all tool permission requests.                                                                                                                                                              |
| `--sandbox`                       | OS containment; since 1.4.4 it has no effect if unavailable.                                                                                                                                             |

Other useful flags are `--add-dir` (repeatable), `--agent`, `-i`/`--prompt-interactive`, `--project`, `--new-project` and `--log-file` ([reference](https://antigravity.google/docs/cli/reference)). Permission posture is otherwise a settings concern: `toolPermission` (`request-review` by default, `proceed-in-sandbox`, `always-proceed`, `strict`), `trustedWorkspaces`, and rule entries like `command(git)`. Because the default mode became Auto in 1.5.7 (users can restore Default with `"agentMode": ""`), an unflagged launch behaves differently across versions. BiBCode should therefore pass `--mode` explicitly only when the user chose one, and otherwise leave the CLI's own default alone.

First launch asks for a colour scheme, a rendering mode (Alt-Screen or Inline) and workspace trust ([Getting started](https://antigravity.google/docs/getting-started?tab=cli)). These prompts appear inside the embedded terminal, so BiBCode should not try to answer them. It should render them like any other TUI and document that the first run per workspace is interactive. The `altScreenMode` setting (`default|always|never`) controls rendering, and `AGY_CLI_DISABLE_AUTO_UPDATE` is the one environment knob worth setting if the host wants a stable binary during a session. Sign-in opens a browser, or prints a URL over SSH. Credentials go to the OS keyring (Windows Credential Manager, a macOS Keychain item named "Antigravity CLI"), and WSL falls back to token files ([Troubleshooting](https://antigravity.google/docs/cli/troubleshooting); [README](https://github.com/google-antigravity/antigravity-cli)). That means a terminal-first integration needs no credential handling at all: the user signs in inside the PTY.

## Signals a host can observe, and what each costs

The documented status signals fall into two groups: those BiBCode can read without touching the user's configuration, and those that need an edit to shared files under `~/.gemini`. In the first group is the terminal byte stream itself. Version 1.4.0 added terminal status reporting over OSC 7501 (working, waiting, done, failed), and 1.5.10 fixed a "done" shown while background work was still running ([CHANGELOG](https://raw.githubusercontent.com/google-antigravity/antigravity-cli/main/CHANGELOG.md)). A third-party release aggregator adds that the CLI queries the terminal for support first, and that `AGYCLIOSC7501=on|off` and `AGYCLIOSC7501MESSAGES=brief` exist ([release note](https://www.havoptic.com/r/antigravity-cli-1.4.0)). The exact payload, the query format, and whether those variables are official are unconfirmed, so BiBCode should record the raw OSC 7501 and BEL bytes during the first experiments rather than design a parser. The `notifications` setting, off by default, rings the terminal bell and raises a desktop notification when the agent needs approval or an answer, or finishes its turn ([Settings](https://antigravity.google/docs/settings.md)).

The second group is richer but invasive. A `statusLine` command in `~/.gemini/antigravity-cli/settings.json` runs on each agent-state change (at most every 300 ms, 5 s timeout, disabled after 30 consecutive failures) and receives JSON with `conversation_id`, `transcript_path`, `agent_state` (`idle`, `working`, `tool_use`, `reviewing`, `authenticating`, `initializing`, `error`) and `tool_confirmation_pending` ([Statusline doc](https://antigravity.google/docs/cli/statusline.md)). That last field is the only documented machine-readable "waiting for approval" signal besides OSC 7501 and the bell. A `title` script receives the same payload ([Title doc](https://antigravity.google/docs/cli/title.md)). Hooks have six events (`SessionStart`, `PreToolUse`, `PostToolUse`, `PreInvocation`, `PostInvocation`, `Stop`) read from `.agents/hooks.json` or `~/.gemini/config/hooks.json`, and their stdin carries `conversationId` and `transcriptPath` ([Hooks doc](https://antigravity.google/docs/hooks.md)). There is no notification, permission-request or prompt-submit event, and no per-launch flag or environment variable for supplying hooks. Community tools such as workmux derive working and done from `PreInvocation` and `Stop` with `fullyIdle:true`, and they show no waiting state ([workmux](https://workmux.dev/guide/status-tracking.md)). Session transcripts live under `~/.gemini/antigravity-cli/brain/<conversationId>/.system_generated/logs/transcript.jsonl`, but the file may not exist yet and its schema is undocumented. The config root is shared with Gemini CLI and the IDE, so any BiBCode edit there affects other tools.

## Headless and ACP: two programmatic doors, one clearly better

Headless mode is documented in depth ([Headless](https://antigravity.google/docs/cli/headless.md)). `agy -p` runs one prompt and exits. `--output-format stream-json` emits NDJSON with an `init` event, many `step_update` events and a `result`. A true multi-turn mode runs without `-p`, using `--input-format stream-json` with `{"event":"user","message":{"content":"..."}}` lines on stdin. That mode has no tool-permission round trip, since approvals are policy-based and unobtainable ones are denied with exit 0. Reliability is the problem: a `-p` hang without a TTY was reported on 1.2.0, 1.2.3 and Windows 1.4.10 and closed as obsolete without a confirmed fix ([#318](https://github.com/google-antigravity/antigravity-cli/issues/318)), and an earlier silent-stdout-loss bug was closed in July ([#76](https://github.com/google-antigravity/antigravity-cli/issues/76)). Headless is suitable for BiBCode's one-shot utility calls but not for a permissioned chat panel.

`agy acp` is the right chat transport. It speaks ACP protocol version 1 over stdio as "Antigravity ACP Server", and editors launch it with command `agy` and args `["acp"]` ([Other editors (ACP)](https://antigravity.google/docs/ide/extensions/acp/)). Flags after `acp` include `--add-dir`, `--agent`, `--sandbox`, `--dangerously-skip-permissions`, `--process-per-session` (needed for HTTP MCP servers the client supplies), `--login`, `--log-file` and `--disable-telemetry`. Logs go to `~/.gemini/antigravity-cli/log/acp-*.log`. A real initialize response from 1.5.9 shows `loadSession:true`, prompt capabilities for images and embedded context but not audio, session capabilities for resume, close, load, list and additional directories, and a logout capability. It also shows duplicate snake_case keys, no `mcpCapabilities`, and no `authMethods` in the reported excerpt ([#1604](https://github.com/google-antigravity/antigravity-cli/issues/1604)). The docs list five auth method ids: `oauth-personal`, `oauth-business`, `gemini-api-key`, `agent-platform` and `terminal-login`. Unauthenticated calls fail with JSON-RPC `-32000` "Authentication required", and `agy acp --login` runs a code-paste sign-in that also works over SSH. Reuse of credentials cached by an interactive `agy` session is documented.

The version history is short. Third-party tracking dates `agy acp` to 1.5.0 (4 Nov 2026), "every model works in any ACP client" to 1.5.1, and Auto mode plus session fixes to 1.5.4 ([release tracker](https://www.havoptic.com/releases/antigravity-cli/2026/11)). The docs state no minimum version and only say to run `agy acp --help`. A sensible gate is 1.5.4 or later. The open bugs matter more than the version. Provider failures (401, 429, 504, dropped streams) end `session/prompt` with `stopReason: end_turn` and the error only as warning text in a message chunk, so quota exhaustion looks like a normal reply ([#1570](https://github.com/google-antigravity/antigravity-cli/issues/1570)). `session/load` replays no history ([#1672](https://github.com/google-antigravity/antigravity-cli/issues/1672)), and `session/list` can return desktop-app sessions that then fail with `-32603` "trajectory not found". `authenticate` can open a browser even with a valid token, and with no display it fails with `-32603` "No browser is available here" ([#1637](https://github.com/google-antigravity/antigravity-cli/issues/1637)). A subagent's `run_command` can time out without ever asking permission ([#1658](https://github.com/google-antigravity/antigravity-cli/issues/1658)). Sessions can wedge after an `ask_question` plus load ([#1581](https://github.com/google-antigravity/antigravity-cli/issues/1581)). ACP also failed on ARM Linux hosts with a 39-bit address space, which Google staff called known (forum thread below). Compared with `cursor-agent acp` and `gemini --acp`, the lifecycle is the same, so an existing ACP client needs only per-provider command, auth ids and extension handling.

## SDKs do not fit, and the terms fit the terminal better than the panel

The official SDK is `google-antigravity` on PyPI: Apache-2.0, Alpha, Python 3.10+, 25 releases since May 2026, with platform wheels that carry a compiled runtime binary ([PyPI](https://pypi.org/project/google-antigravity/)). It uses the same harness as the CLI and the Antigravity 2.0 app ([SDK launch blog](https://www.antigravity.google/blog/introducing-google-antigravity-sdk)), but it authenticates only with `GEMINI_API_KEY` or Agent Platform (Vertex) credentials, and no consumer sign-in is documented. TypeScript and Go are roadmap items only, and Google's maintainers closed a request to host a Node port in the main repository ([issue #31](https://github.com/Google-Antigravity/antigravity-sdk-python/issues/31)). A community Rust crate reportedly drives the bundled `localharness` Go binary, but no wire protocol is documented ([docs.rs snippet](https://docs.rs/crate/antigravity-sdk-rust/0.1.4/source/justfile)). Embedding it would mean shipping Python or reverse-engineering an undocumented protocol. The other official surfaces do not help either. Managed Agents in the Gemini API run in Google's cloud sandbox with no local file access, are in preview, and are billed per token ([docs](https://aistudio.google.com/docs/custom-agents)). `@google/genai` (3.6.1) is only a model client. Gemini CLI is now an enterprise and API-key product (consumer access ended 18 June 2026), is Node-based, and has no official SDK package: `@google/gemini-cli-sdk` returned a 404 ([announcement](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)). Community ACP adapters such as `agy-acp` scrape the CLI's conversation database, and their own disclaimer warns of terms-of-service risk.

The terms are the sharpest constraint, and Google's own materials conflict. The terms treat using the service "in connection with products not provided by us" as grounds for suspension ([terms](https://antigravity.google/terms)). The FAQ says third-party tools accessing Antigravity violate the terms, and that wrapping `agy` in third-party coding agents "isn't supported on consumer plans", pointing such users to Gemini Enterprise or an AI Studio API key ([FAQ](https://antigravity.google/docs/faq)). Yet the headless and ACP docs invite programmatic use and describe five editors doing exactly that. A forum reply written on Google's behalf on 2 November 2026 said the official, unmodified ACP server is supported for single-user interactive development and compliant use "will not cause a suspension", while custom wrappers and non-ACP integrations must use an API key or Enterprise ([forum](https://discuss.ai.google.dev/t/197131)). An earlier reply of unverified staff status lists proxying OAuth tokens, wrapping `agy -p` in agent loops and account rotation as suspension triggers ([forum](https://discuss.ai.google.dev/t/192027)). Reports of 403 "disabled for violation" after OAuth-proxy tools exist ([forum](https://discuss.ai.google.dev/t/code-403-message-this-service-has-been-disabled-in-this-account-for-violation-of-terms-of-service/128101)). The terminal integration is the safest reading: BiBCode is only a terminal emulator, and the user runs Google's own TUI and signs in themselves. A chat panel built on `agy acp` is the pattern the staff reply tolerates, but whether a distributed desktop app counts as "single-user interactive development" is not established. Quotas also stay shared with the user's other use and are not predictable ([plans](https://antigravity.google/docs/plans)).

## Windows and cross-platform differences

Windows differs in install directory (the reports conflict), in `--mode auto` (1.4.4+ instead of 1.3.5+), and in many quoting fixes: hook commands containing double quotes (1.5.8), `!` command quoting (1.5.9), and `EDITOR` paths with backslashes (1.5.8) ([CHANGELOG](https://raw.githubusercontent.com/google-antigravity/antigravity-cli/main/CHANGELOG.md)). An open issue reports that `run_command` subprocesses share the TUI's console and can write stderr over it ([#1690](https://github.com/google-antigravity/antigravity-cli/issues)), which is a ConPTY-adjacent risk for an embedded terminal. The sandbox blocks reads of `AppData\Roaming` since 1.5.10, and the status line and hooks run via `cmd /c` on Windows rather than `sh -c`. No document covers TERM or truecolor requirements, ConPTY behavior, or standard proxy environment variables. macOS and Linux share the curl installer, and Linux adds the ARM 39-bit address-space ACP failure noted above. Because all of these are reported rather than tested, the terminal launcher should be validated once per platform before the integration is called supported.

## Recommendations

For the terminal integration, add an "Antigravity" AI Terminal that spawns the resolved absolute path of `agy` with no arguments, in a PTY, with the project directory as working directory. Pass flags only for explicit user choices: `--model`, `--effort`, `--mode`, and either `--conversation <id>` or `-c` for resume. Do not pass `--dangerously-skip-permissions` or `--sandbox` by default, and never inject them silently. Before first launch, run `agy --version` and `agy --help` on every candidate to filter out the IDE launcher, and offer a path override. Probe and record, on each platform, the first-run prompts, the raw OSC 7501 and BEL output with and without `AGYCLIOSC7501=on`, and what the TUI does on resize. Document the shared `~/.gemini` config root, the first-run prompts, sign-in inside the terminal, the version-dependent default mode, the update behavior, and the consumer-plan terms warning. Do not edit `settings.json`, `hooks.json` or MCP configs without explicit consent, do not store, read or proxy Google credentials or keyring entries, do not rotate accounts, do not scrape `conversations/` or the transcript database, and do not wrap `agy -p` as a general agent loop. If status is wanted early, prefer passive OSC 7501 and BEL detection over a hook or status-line install, and treat a consented `statusLine` command as a later opt-in.

For the later chat provider, speak ACP v1 to `agy acp [--add-dir ...]` over stdio, reusing the generic ACP client that handles other providers, and configure only the command, auth method ids and the `ask_question` extension. Require 1.5.4 or later, check `agy acp --help` at startup, and handle both camelCase and snake_case capability keys. Assume `authMethods` may be missing: on `-32000`, send the user to an interactive `agy` or `agy acp --login` in an embedded terminal rather than silently opening a browser. Persist BiBCode's own transcript because load and resume replay nothing. Scan agent message text for provider and quota errors, because the stop reason will not report them. Filter out foreign sessions from `session/list`. Use `--process-per-session` only if BiBCode must pass HTTP MCP servers. Exclude the SDK, Managed Agents and Gemini CLI paths. Offer API-key and Agent Platform credentials as the officially supported alternative for users on consumer plans, and obtain a written answer from Google before shipping the chat provider to the public.

## Open questions and conclusion

Several points remain unconfirmed. The install page and changelog were partly read through summaries, so flag spellings, the Windows install directory and any winget, npm or Homebrew packages for the CLI are unverified. No official source names the version in which the IDE launcher was renamed, or says how `agy` and the IDE launcher behave when both are installed. The OSC 7501 payload, the query handshake and the official status of the `AGYCLIOSC7501*` variables are undocumented. Hook exit-code semantics, hook environment variables, whether `.agents/hooks.json` needs workspace trust, and the transcript and conversation file formats are unknown. The ACP method names for model, mode and plan updates are not confirmed from raw traces. The ACP minimum version rests on a third-party tracker rather than the official changelog. Whether the non-TTY `-p` hang affects stdin-stream mode on current versions, and whether the Zed registry's `agy_acp_server` binary differs from the `agy acp` subcommand, are open. The exact text and effective date of the terms, and whether a commercial desktop host qualifies for Google's tolerated ACP use, are also unresolved.

The takeaway is that the integration choice is dominated by policy and maturity, not by capability. The terminal path is nearly free technically and the safest on terms, so it should ship first with the host staying passive. The chat path is technically ready enough through `agy acp`, but a 16-day-old protocol surface, silent error reporting and an unanswered terms question make it a staged, version-gated, bring-your-own-credentials feature, not a default.

## Addendum: how Orca launches Antigravity (read 2026-11-20)

Source: the public `stablyai/orca` repository, `main` branch, read on 2026-11-20.

- Terminal: the detect and launch command is `agy` (`src/shared/agent-launch/catalog/tui-agent-config.ts`). The permission flag for its "full access" choice is `--dangerously-skip-permissions` (`src/shared/agent-launch/permissions/tui-agent-permissions.ts`), the same table that gives Claude `--dangerously-skip-permissions` and Codex `--dangerously-bypass-approvals-and-sandbox`.
- The flag is a visible setting, not hard-coded. Each agent has a permission choice: `own` (no flag, the agent's own configuration), `ask`, `accept-edits`, `auto` or `full-access` (`tui-agent-permission-choice.ts`). An untouched install is on `full-access` for every agent (`agent-launch-permission-seed.ts`), so by default Orca does pass the flag to `agy`.
- Orca writes Antigravity's workspace trust before launch, because the TUI's trust menu would otherwise swallow a pasted prompt (`tui-agent-config.ts`, `preflightTrust`).
- Chat: Orca uses ACP, not an SDK. It runs the host's `agy acp` when its version is at least 1.5.2, adding `--dangerously-skip-permissions` for full access, and otherwise a managed ACP server (`src/main/antigravity/antigravity-acp-launch-spec.ts`, `antigravity-host-acp.ts`). It lists models with `agy models`.
- Its setup guide tells users to confirm `agy --version`, to enter a full path when the CLI is not found, and to keep flags out of the command field (`docs/site/content/docs/agents/antigravity.mdx`).

What this settles for BiBCode: passing `--dangerously-skip-permissions` by default matches Orca's default and BiBCode's other terminals. Orca's difference is that the user can change it per agent; BiBCode has no such setting for any terminal today.
