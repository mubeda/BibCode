# Phase 2: Background Git and index locks

- Goal: A person's own `git add` succeeds while BiBCode polls, Git is asked to stop before it is killed, and BiBCode leaves no `index.lock` behind, with tests on Linux, macOS and Windows (#341).
- Round: 1
- Depends on: none
- Owns: `apps/server/src/git/repository.rs`, `apps/server/src/git/process.rs`, `apps/server/src/process/**`, every `SupervisedRunRequest { .. }` initializer in `apps/server/src` (for the one new field only), `apps/server/src/production/runtime.rs`, `.github/workflows/ci.yml`, `docs/operations/observability.md`
- Must not touch: `apps/server/src/git/status_owner.rs`, `apps/server/src/git/broadcaster.rs`, `apps/server/src/production/git_vcs.rs`, `apps/server/src/git/manager/**` (Phases 3 and 4), `apps/web/**`
- Skills: mstack-diagnose (reproduce the lock before changing anything); test-driven-development (each fix starts from a failing test against real Git)
- Read first: `spec.md` section D (R14 to R17, D6, D13, the #341 assumption under Constraints); `AGENTS.md` (Profiler, Crash, and Trace Coverage: child processes, shutdown, logs); `docs/operations/observability.md` (where a new warning log line is described)
- Checkpoint: `cargo test -p bibcode-server --lib -j 2 background_status_` and `cargo test -p bibcode-server --lib -j 2 git_stop_` exit 0, and `cargo clippy --workspace --all-targets -- -D warnings` reports nothing. A terminal `git add` in a polled worktree no longer fails.

Use the toolchain pinned by the repository (`rustup`), not another `cargo` on `PATH`.
