# Plan: Claude activity probe runs what the launch runs (#195)

Batch `probe`, branch `claude/b3-probe`. Phase 1 plan; nothing implemented yet.

## Acceptance criteria

1. **AC1 (shim dispatch).** When `claude` resolves to a symlinked multi-call
   shim, the activity probe runs the resolved path (not its canonical target),
   so `argv[0]` dispatch answers as Claude, and a Claude launch through the
   shim gets `--include-hook-events --forward-subagent-text`, a hook sink, and
   `actors: true`.
2. **AC2 (stale target entry).** AC1 holds when the cache already holds an
   entry for the shim's target, probed under its real name.
3. **AC3 (launch context).** The probe subprocess runs with the launch's
   environment (same normalization as `spawn_child`) and the launch's working
   directory.
4. **AC4 (mismatch not cached).** A probe whose `--version` output does not
   look like Claude Code's is logged as `outcome = "mismatch"`, is not cached
   (the next launch probes again), and does not run `--help`.
5. **AC5 (diagnosable logs).** Probe lines log the resolved path, the
   canonical path and the search `PATH`, all through
   `diagnostics::profiler::redact::redact_path`. A raw `PATH` is never logged.
6. **AC6 (no silent inheritance).** When a Claude session restarts in the same
   server process with an inherited activity lifecycle and the new driver has
   no hook sink, the live scope reports `actors: false`. It does not keep the
   runtime-observed `actors: true`. Other drivers (Cursor, Grok, OpenCode),
   whose startup `none` means "not known yet", keep today's behavior.

## Root cause (evidence at `develop` 27702287cc)

- `apps/server/src/production/provider_runtime.rs:15888`,
  `let executable = std::fs::canonicalize(&resolved).unwrap_or(resolved);`.
  The probe, its cache key and its log all use the canonical target. For a mise
  shim that is `/usr/bin/mise`, which answers as mise.
- `provider_runtime.rs:16187-16192` (`run_claude_probe`): the probe
  `Command` gets no `envs` and no `current_dir`, so it inherits the server's
  environment and working directory. The launch (`spawn_child_after_spawn`,
  `provider_runtime.rs:12552-12610`) applies the normalized request
  environment and `current_dir(&request.cwd)`.
- `provider_runtime.rs:16096-16125` (`probe_claude_activity_support_uncached`):
  any `--version` output that exits 0 counts. An "unsupported" answer from a
  different program is cached by `finish_claude_probe` (16040) under the
  target's identity (`ClaudeProbeCacheKey`, 15723).
- `provider_runtime.rs:1044-1055` (`apply_startup_capabilities`): a startup
  `ActivityCapabilities::none()` is ignored once capabilities were observed at
  runtime. `ClaudeDriver::start` (17267) reports `none()` exactly when it has
  no hook sink, so an inherited lifecycle (`restart_session`, 9637 →
  launch, 8200-8217) keeps `actors: true` for a process that reports no
  subagents.

## Changes (all in `apps/server/src/production/provider_runtime.rs` unless noted)

1. **Probe identity.** In `probe_claude_activity_support_with_environment`,
   resolve exactly as `spawn_child` does: `normalize_provider_environment`
   over the same request environment, then the same resolver. Keep
   `resolved` as the executable to run. Canonicalize only to read metadata
   for the key. `ClaudeProbeCacheKey` gains `resolved: PathBuf`. `executable`
   stays the canonical path, so `cache_paths()` and the eviction tests read as
   before. `seed_cache` fills `resolved`.
2. **Launch context.** Thread the normalized environment
   (`Arc<[(OsString, OsString)]>`) and `cwd: PathBuf` from `ClaudeDriver::spawn`
   (16676 call site, which passes `&request.cwd`) through
   `probe_resolved_claude_activity_support` → `probe_claude_activity_support_uncached`
   → `probe_claude_thinking_display` / `run_claude_probe_command` →
   `run_claude_probe`. Apply `command.envs(..).current_dir(cwd)` before
   `sanitize_provider_subprocess_environment`. The `open_url` credential
   variables are not passed; the probe does not need them. A shared in-flight
   probe runs with the first caller's environment and directory. This is
   documented in a comment.
3. **Version shape.** Add `looks_like_claude_code_version(&str) -> bool`, which
   is true when the output contains `Claude Code`. Real CLIs print
   `2.1.311 (Claude Code)`. mise prints `2026.10.19 <platform> (<date>)`.
   `probe_claude_activity_support_uncached` returns a new
   `ClaudeProbeError::Mismatch { version }` after `--version`, before
   `--help`. Today the error is a `String`; the plan turns it into a small
   enum or adds a mismatch variant to the result, whichever touches less.
   `finish_claude_probe` does not cache it. The waiting launch gets
   `ClaudeActivitySupport::default()`, as on failure.
   - Fixture impact: about 15 Claude fixtures print a bare `2.1.218` or
     `2.1.231`. They are in `apps/server/tests/production_provider_runtime.rs`
     (14462, 14542, 14959, 14997, 15074, 15175, 15481, 15493, 15655, 15665,
     15718, 15788, 15956), `provider_runtime.rs:20572`, and
     `apps/server/tests/fixtures/claude-provider/targeted-rpc{,-ambiguous}.sh`.
     Each gets ` (Claude Code)` appended, a one-token change per line.
     **Ownership overlap:** these lines are probe fixtures, but other agents
     may edit nearby tests in those files.
   - Alternative, not chosen: also accept output that is only a semantic
     version. That leaves the fixtures unchanged but lets a shim that prints a
     bare version be cached as "unsupported" again.
4. **Logs.** `log_claude_probe_outcome` takes the key and the search path, and
   logs `executable` (resolved), `canonical` and `search_path` through
   `redact_path` on the `finished` (supported or unsupported), `failed`
   (failed or timed out) and new `mismatch` lines. The mismatch line is a
   `warn`: `Claude activity probe found another program; the next launch
   probes again`, with its version. The `launching Claude without activity
   flags` warning also logs the redacted `executable`.
5. **Capability lifecycle.** Add a default method to `ProviderDriver` (trait
   at line 365): `fn startup_activity_capabilities_are_final(&self) -> bool {
   false }`. `ClaudeDriver` overrides it with `true`.
   `apply_startup_capabilities(startup, final)` applies the startup value
   unconditionally when `final`, and keeps today's rule otherwise. The call
   site at 8217 passes `driver.startup_activity_capabilities_are_final()`.
   The trait hunk is the one edit outside the briefed ranges. A field on
   `StartedSession` was rejected because it breaks 8 explicit constructions
   in other drivers and in `tests/turn_delivery_*.rs`. Checked: no runtime
   `SetScope(none)` arrives on Claude's no-hook-sink path.
   `ClaudeActivityInputSource::CapabilityProbe` has no production sender, so
   lines 1048-1049 are the whole cause.

## Tests (unix-gated; helpers gated the same way)

In `apps/server/tests/production_provider_runtime.rs`, through
`ClaudeActivityProbeTestContext`:

- `claude_probe_runs_a_multi_call_shim_by_its_link_name`. A `real/mise.sh`
  script branches on `${0##*/}`. Run as `claude.sh`, it prints
  `2.1.311 (Claude Code)` and all three flags. Run under its own name, it
  prints a mise-shaped version and no flags. `bin/claude.sh` is a symlink to
  it. The `.sh` link name keeps the `PosixShellFixture` `/bin/sh` path, and
  `/bin/sh <link>` keeps `$0` as the link name. Probing through the link
  reports `include_hook_events && forward_subagent_text`. This fails on
  `develop`.
- `claude_probe_of_a_shim_ignores_a_cached_entry_for_its_target`. The same
  script answers under its real name as an old Claude
  (`2.0.0 (Claude Code)`, no flags). Probing the target directly first caches
  an unsupported entry. Probing the link then still reports the flags, and
  `cache_len() == 2`.
- `claude_probe_does_not_cache_another_programs_answer`. A mise-shaped
  `--version` gives default support and `cache_len() == 0`. A call-counter
  file shows a second probe runs again and `--help` never ran. A
  `TraceCapture` shows `outcome=mismatch` with the redacted `canonical` and
  `search_path` fields and no raw `PATH` value.
- Complete caller, `claude_launch_through_a_shim_probes_in_the_launch_environment_and_directory`.
  This runs `probe_context.driver_factory(..)`, then `launch()`, then
  `factory.create(request)` with `binary_path` set to the symlink, a
  `request.cwd` that holds a marker file, and a marker variable in
  `request.environment`. The fixture lists the flags only when `$PWD` holds
  the marker, the variable is set and `$0` is the link. It writes the launch
  arguments to a capture file. The test asserts that the capture contains
  `--include-hook-events` and that `driver.start()` reports `actors: true`.
  This fails on `develop` for all three reasons.

In `provider_runtime.rs` unit tests, through `restart_session` with
`SequencedSupervisorFactory` and `SupervisorDriver` (the template is
`session_restart_cancels_and_reaps_held_late_dispatch_before_replacement_launch`,

- `a_final_startup_none_replaces_runtime_observed_capabilities_on_restart`.
  The first driver starts with `actors: true` and emits a runtime `SetScope`

## Open question for approval

The cache key does not include the working directory. A mise shim with
per-directory versions shares one entry across projects and across Claude
updates behind the shim. If project B pins a Claude that lacks the flags,
B's launch would pass flags its Claude rejects. One option is to add `cwd`
to the key when `resolved != canonical`. That costs one probe of about
0.5 s per new directory for shim users. Not planned unless approved.
